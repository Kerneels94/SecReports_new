1. Editing a user locks them out with no way back in

Problem: backend/src/services/auth.service.ts:748 sets emailVerified: false whenever the request includes an email, even if it's the same address. The admin users page (frontend/src/app/(dashboard)/admin/users/page.tsx:137) always sends the email. So renaming a user or changing their role marks them unverified, and no verification email goes out because the address didn't change (:799). After that, login and refresh both fail (authDenied, :167), and forgot-password ignores unverified users (:568). The user is stuck until someone fixes the record in the database.
Fix: only clear the flag when the email actually changes: data.email !== undefined && data.email !== user.email.

2. Next billing date skips a month

Problem: backend/src/services/subscription.service.ts:18 calls setMonth(+1) before setDate(25). On the 29th–31st, the month rolls past the end of the next month. Repro output:
2026-01-31 -> Mar 25 2026   (should be Feb 25)
2026-03-31 -> May 25 2026   (should be Apr 25)
Existing tests only check Aug 10 and Aug 25, so they miss it.
Fix: swap lines 18 and 19 so it sets the 25th first, then adds the month.

3. Parallel wrong-password attempts never trigger the lockout

Problem: handleLoginFailure (auth.service.ts:114) reads loginAttempts, adds 1 and writes it back. Concurrent failed logins all read the same value, so ten parallel guesses usually end up stored as 1 attempt. The 3-strike lockout never fires, and the login rate limit of 10/min per IP allows this to repeat every minute. That makes password brute-forcing possible.
Fix: use an atomic loginAttempts: { increment: 1 } and decide the lock from the loginAttempts to 0 when locking. Today the count stays at 3 after the lockexpires, so one typo re-locks the account for twice as long.

4. Two open tabs log the user out everywhere

Problem: refresh (backend/src/services/auth.service.ts:299) treats any unknown refresh token as theft: it deletes every refresh token for the user and returns 401. The refresh cookie is shared by all tabs, but the "only one refresh at a time" guard (frontend/src/services/api.ts:7, :68) lives in each tab's own ApiClient. The access token lasts 15 minutes and useAuth calls me() on mount (frontend/src/hooks/useAuth.tsx:34). So when two tabs hit a 401 together (browser restores tabs, laptop wakes up, two tabs opened at once), both send the same cookie. The first rotates it. The second gets "Refresh token has been revoked — all sessions invalidated", clears the shared accessToken in localStorage, and every tab is logged out. If both requests pass findUnique before either deletes, the second prisma.refreshToken.delete throws P2025 and returns 500, with the same result.
Fix: serialize refresh across tabs in attemptRefresh with navigator.locks.request("auth-refresh", ...), so the second tab waits and then sends the already-rotated cookie. In the backend, use deleteMany and treat count === 0 as reuse, so the race gives a 401 instead of a 500.

5. Deleting a user breaks the incident list for the whole company

Problem: deleteUser (auth.service.ts:841) hard-deletes the user. Incident.reporter (backend/prisma/schema.prisma:126) and AuditLog.performedByUser (:273) are required relations with onDelete: NoAction. On MongoDB, Prisma emulates relations and NoAction does nothing, so the delete succeeds and leaves incidents pointing at a missing user. Every query that includes reporter then throws "Inconsistent query result: Field reporter is required to return data, got `null` instead." That covers the incident list (incident.service.ts:169), incident detail (:185), the dashboard (report.service.ts:59), and all CSV/PDF exports (export.controller.ts:476, :640, :683, :790). One deleted reporter makes the incident page show "Failed to load incidents" for everyone in the company. Audit logs filter on performedByUser.companyId (auditLog.service.ts:39), so the deleted user's whole history also disappears from the audit log page.
Fix: soft-delete instead. Set the existing, unused status field to "inactive", delete the user's refresh tokens, reject status !== "active" in authDenied (:155), and hide inactive users in listUsers. Incidents and audit history keep a valid reporter.

6. New incidents default to yesterday's date after midnight

Problem: the new-incident form (frontend/src/app/(dashboard)/incidents/new/page.tsx:54) defaults incidentDate to new Date().toISOString().split("T")[0], which is the UTC date. Users are in South Africa (UTC+2), so from 00:00 to 01:59 every night the default is the previous day. Night-shift control rooms log a lot of incidents in that window, and operators who keep the default file them on the wrong day. On the last night of a month they land in the wrong month in the monthly and yearly stats. Repro with TZ=Africa/Johannesburg:
2026-10-16 00:30 -> 2026-10-15   (should be 2026-10-16)
2026-11-01 00:15 -> 2026-10-31   (should be 2026-11-01, wrong month)
Fix: use the local date: new Date().toLocaleDateString("en-CA"), which gives YYYY-MM-DD in the browser's time zone.

7. Resetting the password does not lift a lockout

Problem: resetPassword (backend/src/services/auth.service.ts:596) only changes passwordHash (:614). It leaves lockedUntil and loginAttempts untouched. The usual path is: a user forgets their password, fails 3 times, gets locked (15 min, doubling up to 4 h), then uses forgot-password. They set a new password and try to log in. authDenied (:165) still sees lockedUntil in the future, so login returns the generic "Invalid email or password" (:212). The user thinks the new password is wrong or the reset failed, and support gets the call.
Fix: in the resetPassword user update, also set loginAttempts: 0 and lockedUntil: null. The reset link already proves the user owns the mailbox, so this does not weaken brute-force protection.

8. A deleted user's email can never be used again

Problem: since the soft-delete fix for #5, deleteUser (auth.service.ts:844) keeps the user row with status "inactive", and listUsers (:671) hides it. User.email is unique, so createUser (:513) finds the hidden row and throws "Email already in use" (:516). The admin sees no user with that email and has no way to restore one; nothing in the code reactivates an inactive user. A rehired employee, or someone deleted by mistake, cannot be added back. Changing another user's email to that address fails the same way (:743). register (:400) returns "Account created" but creates nothing.
Fix: in createUser, if the existing user is in the same company and inactive, reactivate it instead of throwing: set status "active", the new name, password hash and role, emailVerified: false, and send a fresh verification email. Old incidents and audit history stay linked to the same user. Keep the 409 for active users and for users in other companies.

9. Dispatch and arrival times are saved in the server's time zone

Problem: the new-incident form uses datetime-local inputs (frontend/src/app/(dashboard)/incidents/new/page.tsx:126, :133). They produce strings like "2026-10-16T23:50" with no offset, and the form sends them as-is. The backend parses them with new Date() (backend/src/services/incident.service.ts:209-210), which reads an offset-less string as server local time. The browser's offset is lost. On a server running UTC (the usual Ubuntu VPS default; nothing in the repo sets TZ), an operator in South Africa enters 23:50 and gets 23:50 UTC stored. The incident detail modal formats in the browser (IncidentDetailModal.tsx:181, :192) and shows "Oct 17, 01:50 AM", two hours late and on the next day. The PDF export formats on the server (export.controller.ts:135-136) and shows "Oct 16, 11:50 PM". The same incident therefore shows two different times. Repro:
TZ=UTC                  stored 2026-10-16T23:50Z -> modal Oct 17 01:50, PDF Oct 16 23:50
TZ=Africa/Johannesburg  stored 2026-10-16T21:50Z -> modal Oct 16 23:50, PDF Oct 16 23:50
Response-time durations are unaffected, because both times shift by the same amount.
Fix: in onSubmit, convert both fields in the browser before sending: dispatchTime ? new Date(dispatchTime).toISOString() : undefined, and the same for arrivalTime. The server then receives an unambiguous UTC instant. Format PDF times with timeZone: "Africa/Johannesburg" so the server's time zone no longer matters.

10. Double-clicking "Mark Paid" records the payment twice

Problem: markAsPaid (backend/src/services/invoice.service.ts:136) reads the invoice, checks status !== "paid" (:142), then runs a transaction that updates the invoice with no status condition and creates a PaymentHistory row and a ledger "payment" entry (:144-174). The "Mark Paid" buttons in the superadmin portal (frontend/src/app/(admin)/portal/invoices/page.tsx:225, portal/page.tsx:243) are never disabled while the request runs. A double-click sends two requests, both pass the status check, and both record the payment. Total revenue (getRevenueStats sums PaymentHistory, :264), monthly revenue, revenue trends and the ledger net balance all count the invoice twice. Nothing in the UI shows the duplicate.
Fix: inside an interactive transaction, mark the invoice paid with updateMany where status is not "paid", and throw ConflictError when count is 0 before creating the payment and ledger rows. Map a Mongo write conflict (P2034) from the losing transaction to the same ConflictError.

11. Emails are case-sensitive, so users with a capital letter cannot log in

Problem: no auth schema normalises email (backend/src/validators/auth.schema.ts:20, :30, :39, :48, :72), and every lookup is an exact match: login (auth.service.ts:206), forgotPassword (:569), createUser's duplicate check (:514) and register (:398). An admin who creates "John.Smith@acme.co.za" (copied from an email signature) leaves a user who types "john.smith@acme.co.za" with "Invalid email or password". Forgot-password silently does nothing for them, so they cannot recover. The duplicate checks also miss case variants, so "john@acme.co.za" and "John@acme.co.za" can be two separate accounts.
Fix: trim and lower-case email in every auth schema (z.string().trim().toLowerCase().email()). Lower-case SUPER_ADMIN_EMAIL in the seed. Add a one-off migration (prisma/migrate-lowercase-emails.ts) that lower-cases stored user, company and pending reset-token emails and lists clashing case variants instead of merging them.

12. A manager given "Manage users" cannot edit anyone

Problem: the Users page is shown to any role with users.manage (frontend/src/components/layout/Sidebar/index.tsx:23), and the permission matrix lets an admin grant that to managers. The edit form always sends the user's role for non-admin users (frontend/src/app/(dashboard)/admin/users/page.tsx:141), even when it has not changed. updateUser (backend/src/services/auth.service.ts:716) treats any role in the body as a role change: if (data.role) ... actorRole !== "admin" -> "Only an admin can change a user's role". So a manager with users.manage gets that error when they only rename a senior or fix a typo in an email, and cannot edit their own name either.
Fix: treat the role as a change only when it differs: data.role !== undefined && data.role !== user.role. Changing a role still needs an admin, and admins still cannot change their own role.

13. A manager given "Manage users" can make themselves an admin

Problem: updateUser blocks managers from changing roles and emails to "prevent manager→admin takeover" (backend/src/services/auth.service.ts:716-735), but createUser and deleteUser have no such guard. The users.manage permission can be granted to managers. createUserSchema accepts role "admin" (backend/src/validators/auth.schema.ts:41), the controller passes no actor role (backend/src/controllers/auth.controller.ts:86), and createUser saves params.role as given (auth.service.ts:526). The UI only offers manager and senior (frontend/src/app/(dashboard)/admin/users/page.tsx:24) and hides Delete on admin rows (:258), but the API enforces neither. So a manager can POST /auth/users with role "admin" and an email they own, verify it, and log in as an admin. With that account they can change roles, permissions and billing. They can also DELETE /auth/users/:id on the real admin (deleteUser, auth.service.ts:837, only blocks self-delete). Repro: createUserSchema.safeParse({ ..., role: "admin" }).success is true.
Fix: pass request.user.role into createUser and deleteUser. Throw ForbiddenError when a non-admin creates a user with role "admin" or deletes a user whose role is "admin".

14. Every download fails after 15 minutes on the page

Problem: request() in frontend/src/services/api.ts:77 handles an expired access token: on a 401 it refreshes and retries. downloadBlob (:131) does not. It throws "Download failed: 401 ..." on the first 401. The access token lasts 15 minutes. So an operator who opens the incidents page, works on a call, and then clicks Download PDF gets "Failed to download PDF". The same happens for the CSV export, the yearly PDF and the response-time PDF (frontend/src/services/index.ts:147-152). A page reload fixes it, because useAuth's me() call goes through request() and refreshes. Repro with a mocked fetch and an expired token:
get():          /incidents -> /auth/refresh -> /incidents   (works)
downloadBlob(): /export/pdf?incidentId=1 | Download failed: 401 {"error":{"message":"Invalid or expired token"}}
Fix: in downloadBlob, on a 401 run the same refresh as request() (the shared this.refreshing promise and attemptRefresh) and retry once.

15. Downgrading the plan keeps every extra seat

Problem: changePlan (backend/src/services/subscription.service.ts:315) only rejects the free plan. It never compares active users with the new plan's userLimit. The seat limit is checked only when adding a user (canAddUser, :240). The billing page offers every paid plan to the admin (frontend/src/app/(dashboard)/settings/billing/page.tsx:107-118). So a company with 12 users on Enterprise (R4,500) can switch to Professional (R1,500, 5 users) and keep all 12. generateMonthlyInvoices then bills Professional. The billing page shows "Users Used 12 / 5".
Fix: in changePlan, when plan.userLimit > 0, count active users. If the count is above the limit, throw a ForbiddenError such as "You have 12 active users. The Professional plan allows 5. Remove users before changing plan." Show that message in handleConfirmPlan instead of the generic "Failed to change plan".

16. Creating a user with an ordinary password fails with "Invalid input"

Problem: the create-user form only checks min(8) (frontend/src/app/(dashboard)/admin/users/page.tsx:23), and the placeholder says "Min. 8 characters" (:195). The backend requires a lowercase letter, an uppercase letter, a number and a special character (strongPassword, backend/src/validators/auth.schema.ts:8). The register page enforces the same four rules, but the users page does not. AuthController.createUser (backend/src/controllers/auth.controller.ts:86) throws a plain "Invalid input", unlike changePassword (:133), which returns the first issue's message. So an admin who types "guardhouse1" sees "Invalid input" and no hint about what is wrong. Repro: the frontend schema accepts { password: "guardhouse1" } and createUserSchema rejects it.
Fix: use the register page's password rules in the users page schema, and fix the placeholder. In AuthController.createUser, send parsed.error.issues[0]?.message like changePassword does.

17. The audit-log "Deleted" filter never finds a deleted user

Problem: the action dropdown is built from ACTION_LABELS (frontend/src/app/(dashboard)/admin/audit-logs/page.tsx:17-32, :152). It offers "update", "delete" and "status_change", which nothing in the backend logs. It leaves out actions that are logged: user_deleted (backend/src/services/auth.service.ts:857), email_verified, report_email_sent, report_batch_email_sent and report_response_time_exported. An admin who wants to know who removed an employee picks "Deleted" and gets "No audit log entries found." Rows for those actions show raw keys such as "user_deleted" in the Action column.
Fix: make ACTION_LABELS match the actions the backend writes. Remove update, delete and status_change. Add user_deleted ("User Deleted"), email_verified and the three report actions.

18. The incident list shows the date the report was typed, not the incident date

Problem: the Date column in the incidents table (frontend/src/app/(dashboard)/incidents/page.tsx:293) shows incident.createdAt. The Date From and Date To filters on the same page filter on incidentDate (backend/src/services/incident.service.ts:159-163), and the detail modal and the PDF file name also use incidentDate. So an incident that happened last night and was logged this morning shows today's date in the list. Filtering on yesterday returns rows that all show today's date, and filtering on today hides them. Night shifts that log incidents after the fact, and anyone who backfills, see dates that match neither the filter nor the PDF. Repro with TZ=Africa/Johannesburg:
incidentDate 2026-10-15, createdAt 2026-10-16T06:10Z -> filter 2026-10-15 returns the row, row shows 2026/10/16
Fix: show incidentDate in that column. It is stored as UTC midnight, so format it with { timeZone: "UTC" } so it never shifts by a day.

19. A failed download replaces the whole page with an error

Problem: the dashboard's yearly PDF handler (frontend/src/app/(dashboard)/dashboard/page.tsx:139) sets the page's load error. The if (error) branch (:171) then replaces every stat and chart with "Failed to download PDF" and a Retry button that reloads the dashboard. The comment at :64-66 says download failures must not do this, and the response-time download (:154) already uses downloadError, but the yearly PDF was missed. The incidents page does the same (incidents/page.tsx:96): one failed PDF download wipes the incident table until the user clicks Retry. In IncidentDetailModal (frontend/src/components/incidents/IncidentDetailModal.tsx:89) the incident details are replaced by the error, and "Try again" reloads the incident instead of retrying the download. Any 403 (expired trial, permission removed), 404 or network drop during a download triggers it.
Fix: give each download its own error state shown next to its button, as downloadError does on the dashboard. Keep the existing error state for load failures only.

20. The dashboard skips months with no incidents

Problem: monthlyStats (backend/src/services/report.service.ts:85-101) returns only months that have incidents. The dashboard (frontend/src/app/(dashboard)/dashboard/page.tsx:111-121) treats the last two entries as "this month" and "previous month", and the trend chart plots the list as it comes. When a month has no incidents, the stat card compares against an older month and shows the wrong direction, and the chart drops that month from the x-axis, so a quiet month disappears instead of showing 0. Repro:
data Jun 5, Aug 3 (Jul 0) -> card "Aug 2026 incidents 3, ▼ 2 vs previous month" (should be ▲ 3); chart axis 2026-06, 2026-08
Fix: fill the gaps with 0 in the dashboard (fillMonthGaps) before chartData and latestMonth use the data, covering every month from the first entry to the last. The API stays unchanged.

Side effects

- The fix for #1 touches only updateUser.
- The fix for #2 changes due dates shown in billing details.
- The fix for #3 changes when lockout escalates, so some lockout tests may need updating.
- The fix for #4 needs the Web Locks API, which all current browsers support. Tests that mock fetch in api.ts will need a navigator.locks stub.
- The fix for #5 changes deleteUser's behaviour and its tests. Records already left dangling by earlier deletes need a one-off cleanup; the fix does not repair them.
- The fix for #6 changes only the default value. Dates users pick by hand are unaffected.
- The fix for #7 touches only resetPassword. lockoutCount is kept, so a later lockout still escalates.
- The fix for #8 changes createUser only when the match is inactive. The existing canAddUser call at the top of createUser still runs first, so reactivating a user counts against the seat limit.
- The fix for #9 applies only to new incidents. Times already stored stay shifted by the server's offset and need a one-off correction if the server ran in UTC.
- The fix for #10 needs MongoDB transactions (a replica set), which resetPassword and verifyEmail already rely on. The second of two concurrent clicks now gets a 409 "Invoice already paid". Duplicates recorded before the fix are not removed.
- The fix for #11 needs the migration run with the deploy: until it runs, users stored with capitals cannot log in, because the input is now lower-cased. Clashing case variants the script lists must be merged by hand.
- The fix for #12 also lets an admin save their own record when the form sends their unchanged role.
- The fix for #13 changes the createUser and deleteUser signatures, so their callers and tests need the extra actor role argument. Admin-created users and admin deletes are unaffected.
- The fix for #14 touches only downloadBlob. If the refresh also fails, the download still fails, as it does today.
- The fix for #15 blocks downgrades for companies already over the new plan's limit until they remove users. Companies that already downgraded this way are not corrected.
- The fix for #16 changes only form validation and the error text. Existing passwords are unaffected.
- The fix for #17 changes only the dropdown and labels. Old rows keep their stored action keys.
- The fix for #18 changes only the displayed date. Rows sort by createdAt as before, so a backfilled incident can appear above newer ones.
- The fix for #19 touches only the three download handlers. Load errors still show the Retry view.
- The fix for #20 fills only the months between the first and last month with incidents. If the current month has none yet, the card still shows the last month that had incidents. The yearly view is unaffected, because zeros add nothing to its totals.
