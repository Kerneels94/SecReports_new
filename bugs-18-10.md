1. A user who misses the verification email can never log in

Problem: the verification link expires after 24 hours (backend/src/services/auth.service.ts, register and createUser), and there is no endpoint to resend it. Registering again with the same email returns "Account created. Please check your email to verify your account." but sends nothing, because register stops at the existing user. forgotPassword skips unverified users (:576), so a reset email never goes out either. Login and refresh both reject unverified users (authDenied). So if the email lands in spam, or the user opens it a day late, the account is locked for good and the email address can never be registered again. Admin-created users can be deleted and recreated by their admin; a company owner who registered themselves has no way out short of a database edit.
Fix: let forgotPassword send a reset link to unverified active users (drop !user.emailVerified from the guard at :576), and set emailVerified: true in the resetPassword user update (:623). The reset link proves the user owns the mailbox, so this is the option golden rule #32 already allows.

2. Behind Nginx, every user shares one rate-limit bucket

Problem: Fastify is created without trustProxy (backend/src/app.ts:35). The README deploys the API on the VPS behind Nginx with Let's Encrypt, so Node sees every request as coming from 127.0.0.1. All per-IP rate limits then apply to the whole platform at once: 10 logins per minute for every user of every company (auth.routes.ts:12), 5 registrations, 5 password resets, and 100 requests per minute in total (app.ts:65). A few operators loading the dashboard hit the global limit, and anyone who sends 10 bad logins a minute blocks every login on the platform. The audit log also stores 127.0.0.1 as every user's IP (auditContext, app.ts:72).
Fix: Fastify({ logger: true, trustProxy: "127.0.0.1" }), using the address Nginx connects from. Do not use trustProxy: true if Node is also reachable directly, or clients can fake X-Forwarded-For and dodge the limits. This depends on the Nginx setup, which is not in the repo.

3. The "Date To" filter leaves out the selected day

Problem: the incidents page sends dateTo from an <input type="date"> (frontend/src/app/(dashboard)/incidents/page.tsx:203), so the value is "2026-03-15" with no time. IncidentService.list (backend/src/services/incident.service.ts:162) turns it into new Date("2026-03-15"), which is 00:00 UTC, and filters with lte. Every incident later that day is dropped. Picking the same day for From and To shows an empty list. Repro:
dateTo=2026-03-15 -> 2026-03-15T00:00:00.000Z
2026-03-15T00:00:00Z kept: true
2026-03-15T08:30:00Z kept: false
2026-03-15T21:50:00Z kept: false
Fix: make the upper bound the start of the next day: incidentDate.lt = new Date(Date.parse(params.dateTo) + 86_400_000).

4. Turning off emailed reports for a role does not stop them

Problem: the permission catalog puts emailed reports under export.reports ("Yearly & emailed reports", backend/src/lib/permissions.ts:61-64). But POST /reports/email and POST /reports/batch-email check reports.view (backend/src/routes/report.routes.ts:17-24), and so does the email button (frontend/src/app/(dashboard)/incidents/page.tsx:24). An admin who switches off "Yearly & emailed reports" for seniors on the Permissions page still lets them email incident CSVs and PDFs, including every attempted or positive incident at once, to any address. Seniors also cannot download CSV/PDF (export.csv defaults to admin and manager), yet they can email the same files out by default.
Fix: check requirePermission("export.reports") on both email routes and use hasPermission(user, "export.reports") for canEmail. Both keys default to admin, manager and senior, so nobody loses access today; the toggle simply starts working. If seniors should never send files out, use export.csv instead.

5. Bad ids and dates return 500 instead of 400 or 404

Problem: every :id route passes the raw param to Prisma, and the id fields are ObjectIds. GET /incidents/abc makes Prisma throw P2023 (malformed ObjectID). The error handler (backend/src/app.ts:157) only maps P2002, so the request becomes a 500, an error log entry and a PostHog backend_error. Dates fail the same way: createIncidentSchema accepts any string for incidentDate, dispatchTime and arrivalTime (backend/src/validators/incident.schema.ts:15-20), and paginationSchema accepts any string for dateFrom and dateTo (:39-40). incidentDate: "tomorrow" becomes an Invalid Date, Prisma rejects it, and the user gets a 500. Admin invoice and ledger ids, audit log dates and invoice dates behave the same way.
Fix: in setErrorHandler, map P2023 and P2025 to a 404 NOT_FOUND next to the P2002 branch. Validate the incident and pagination date fields with the isoDate refine that already exists in backend/src/validators/ledger.schema.ts:9 (move it to a shared spot).

6. Emailing a report without an incident id sends a random incident

Problem: ExportController.email (backend/src/controllers/export.controller.ts:773) casts the body without validating incidentId. If it is missing, findFirst receives where: { id: undefined, companyId }. Prisma ignores undefined fields, so the query matches the company's first incident and emails it to the given address, with the attachment named incident-undefined.pdf. The same handler and batchEmail (:658) check email and format with hand-written regexes instead of Zod.
Fix: add one Zod schema for the email body (incidentId: z.string().min(1), email: z.string().email(), format: z.enum(["csv", "pdf"])) and one for batch-email, and delete the hand-written checks. verifyEmail (auth.controller.ts:78) and changePlan (subscription.controller.ts) also read their bodies without validation and should get the same treatment.

7. One PDF export can stall the server for every company

Problem: GET /export/pdf without incidentId (export.controller.ts:628) renders every incident of the company into one PDF, one page each, held in memory. POST /reports/batch-email with format "pdf" (:658) does the same for every attempted or positive incident. pdfkit draws on the main thread, so a large company's export blocks every other request on the server until it finishes, and the attachment can exceed the mail provider's size limit. The UI always sends incidentId to /export/pdf, so the all-incidents path is only reachable by calling the API directly. /export/pdf, /export/csv and /export/yearly-pdf have only the global rate limit; /export/response-time-pdf already has 10 per minute.
Fix: require incidentId on /export/pdf and delete the multi-incident branch. Cap the batch query with take: 500. Add config: { rateLimit: { max: 10, timeWindow: "1 minute" } } to the csv, pdf and yearly-pdf routes.

8. One DNS hiccup blocks a whole email domain for an hour

Problem: hasMxRecord (backend/src/lib/email.ts:18) caches false for one hour on any DNS error, including timeouts and server failures. If one lookup of gmail.com times out, every registration, user creation and email change with a Gmail address fails with "Email domain does not accept mail" for the next hour, in that process.
Fix: cache false only when the error code is ENOTFOUND or ENODATA. For other errors, return false without caching, so the next request tries again.

9. Every superadmin login logs a database error

Problem: login calls SubscriptionService.checkAndNotifyTrialEnding(user.companyId!) (backend/src/services/auth.service.ts:224). A superadmin has no company, so companyId is null, and findUnique({ where: { companyId: null } }) throws a Prisma validation error. The .catch logs "[AuthService] Trial notification failed" on every superadmin login. requirePermission (backend/src/middleware/requirePermission.ts:24) has the same problem: a superadmin calling a company route gets a 500 instead of a 403.
Fix: only call checkAndNotifyTrialEnding when user.companyId is set. In requirePermission, throw ForbiddenError when companyId is null before querying.

10. Incident reference numbers will start to collide

Problem: generateReferenceNumber (backend/src/lib/utils.ts:13) uses 3 random bytes, so there are 16.7 million numbers per year, and referenceNumber is unique across all companies (schema.prisma:101). When two incidents draw the same number, the create fails with 409 "A record with that unique value already exists" and the operator has to submit again. Chance of at least one collision in a year, over all companies:
1000 incidents/yr -> 0.03
5000 incidents/yr -> 0.53
Fix: use crypto.randomBytes(4) (4.3 billion numbers per year). Existing numbers stay valid.

11. The CSV formula guard misses tab and carriage return

Problem: sanitizeCsv (backend/src/controllers/export.controller.ts:67) neutralises cells starting with =, +, - or @. OWASP's CSV injection list also includes a leading tab and a leading carriage return, which some spreadsheet programs skip before reading a formula. An incident title that starts with a tab followed by = is exported as a live formula.
Fix: change the pattern to /^[=+\-@\t\r]/.

Side effects

- The fix for #1 makes a password reset also verify the email. Admin-created users who never verified can now reset and log in without asking their admin.
- The fix for #2 changes request.ip for rate limiting and audit logs only. Audit rows already stored keep 127.0.0.1.
- The fix for #3 touches only the incident list. Incidents stored at exactly 00:00 on the day after dateTo are now excluded, which is correct.
- The fix for #4 changes no access by default. Companies that already switched off export.reports for a role will see that role lose the email buttons.
- The fix for #5 changes error responses only. Clients that showed a generic error on 500 now get 404 or 400.
- The fix for #6 makes the email routes return 400 for a missing or malformed incidentId instead of sending a report.
- The fix for #7 removes the all-incidents PDF from the API and caps batch PDFs at 500 incidents. CSV export is still unlimited.
- The fix for #8 means a domain with a short DNS outage is retried on every request instead of being cached.
- The fix for #9 changes no behaviour for company users.
- The fix for #10 makes new reference numbers two characters longer.
- The fix for #11 adds a leading space to cells that start with a tab or carriage return.
